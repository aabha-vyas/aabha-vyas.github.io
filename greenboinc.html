GreenBOINC

Fall 2025carbon-aware scheduling for volunteer computing · Python, Flask · CS 598 project with Siddesh Vijayakumar and Sri Valluri

BOINC is UC Berkeley's open-source volunteer computing platform. It breaks scientific workloads like astrophysics searches and molecular simulations into small tasks, and millions of donated laptops, desktops and servers run them. Cloud providers already cut emissions by scheduling work around the grid. BOINC doesn't do this at all.

GreenBOINC adds carbon-aware scheduling to BOINC. Volunteer machines run at different times and sit on different power grids, so the same work can be done with less carbon if you pick when and where it runs.

why it's a different problem

Carbon-aware systems for datacenters, like CARBON-DQN (deep RL for VM placement) and EDJC (long-term carbon budgeting across regions), assume they control the infrastructure. They can migrate jobs, scale up and down and place VMs. A volunteer network gives you none of that. Hosts come and go, the hardware varies, and each owner decides when their machine runs. GreenBOINC has to work within those limits.

the signal: MOER

MOER (marginal operating emissions rate) measures the emissions from the next unit of electricity drawn from the grid. A low-MOER period is a "clean window." Running work in clean windows is the idea behind both schedulers.

how it works

temporal shifting: when to run

A local Flask server wraps the BOINC client API on each volunteer machine. Every hour it pulls the MOER forecast for the machine's grid region from the WattTime API, averaged to hourly slots, and picks the cleanest hours. If a volunteer wants to donate, say, 30% of the day, the scheduler puts that 30% in the lowest-MOER hours instead of whenever the machine happens to be idle.

spatial shifting: where to run

A central coordinator collects "votes" from clients: each client's average grid emissions, its uptime and the projects it can run. We benchmarked the power draw of six BOINC projects on our own hardware. They ranged from 34 W (Moo! Wrapper) to 137 W (PrimeGrid Genefer). The coordinator solves a min-cost-flow problem with Google OR-Tools. Projects supply work weighted by votes and uptime, clients take work up to their uptime, and each unit costs task wattage × the client's emissions. Every project still gets its requested runtime, but power-hungry tasks go to clients on cleaner grids.

limits

  • Temporal results cover one grid region, Northern California, which has unusually large daily swings.
  • Spatial results come from simulation, not live volunteers. The real-country runs use annual average intensity per country, not live marginal rates.
  • The simulations are randomized, so reruns vary by up to a few percentage points.
  • The two schedulers were tested separately, not together.
