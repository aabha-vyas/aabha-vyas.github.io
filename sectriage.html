SecTriage

in progressa security-triage agent and eval harness · Python 3.12 · started October 2026

I'm building an agent that triages code for security findings, and an eval harness that scores it. The agent reads a local, intentionally vulnerable codebase with two tools, read_file and search_code, and reports findings in five classes: SQL injection, XSS, path traversal, command injection and hardcoded secrets. Every report is checked against a ground-truth file.

I chose security triage because the answers are checkable. A bug is either in the code at a known location or it isn't, so I can measure precision, recall and cost per run instead of judging the agent by feel.

how it works

the agent

A loop in plain Python with a budget on steps, cost and time. Every step appends one event to a JSONL log with the model output, tool call, result, tokens and cost, and every run records why it stopped.

the evaluation

Four small seeded apps with planted bugs, decoy code that looks dangerous but is safe, and one app with no bugs to catch false alarms. The target files are frozen with SHA-256 hashes and a test fails if any file changes, so I can't quietly tune toward them. A baseline gate refuses to compare runs whose setup differs, instead of reporting a fake regression.

the infrastructure

A SQLite task queue with a worker pool, lease tokens and an atomic ack, so a worker that loses its lease can't write a result. A demo kills a worker mid-task and the run still finishes with one result row after two attempts. Replay from the event log serves recorded model turns with no API call. Commands can run in a Docker sandbox with no network, a read-only filesystem, dropped capabilities and CPU, memory and process limits.

Model claude-haiku-5-5, prompt v1, no sandbox, 5 runs per row, 5 planted bugs per target. All 40 runs finished cleanly with no false positives.

It caught command injection but missed every SQL injection, path traversal and hardcoded secret. Read this carefully: Semgrep was one deterministic run over three targets and the agent rows are 5 runs per target, so the rows are not like for like.

a prompt change that didn't ship

I tried a v2 prompt with one added instruction: report each finding as soon as it is verified. I wrote five success criteria before running it. It met 2 of 5 on ledger_api and 1 of 5 on notes_portal, so v1 stayed the default. At 15 steps recall rose from 0.44 to 0.72 and from 0.40 to 0.76, but at 30 steps notes_portal recall fell from 0.92 to 0.84 and one of the 40 runs had a false positive.

limits

  • Four small seeded apps with at most 5 planted bugs each, one model and 5 runs per cell. These numbers say nothing about real codebases.
  • Only the five bug classes are scored. Patch quality isn't measured yet.
  • The eval runs used no sandbox. The sandbox is tested, but no run has had the model choose to use it on its own.

next

Sweeping the model as well as the step budget, and running the agent through the sandbox on its own, to see where it breaks. A score that is always perfect doesn't tell you anything.

why I built it this way

At CME I work on messaging infrastructure, so I already care about ordering, replay, latency and failure recovery. SecTriage applies those habits to AI workloads: treat measurement as the product, keep frozen data, and be honest about limits.
